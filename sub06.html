Hanssem Redesign

한샘 공식몰을 Next.js App Router로 처음부터 재설계한 프로젝트.
기존 디자인의 정보 요소(가격·할인율·배지·리뷰)는 유지하면서, 구조와 인터랙션을 절제된 톤으로 다시 제작했습니다.

Duration: 2026.06 – 2026.08
Role: UI/UX Design, Web Publishing, Frontend 100%
Tool: Figma, Google Flow, Claude Design&Code
Tech Stack: Next.js (App Router), TypeScript, CSS Modules, Zustand

Problem

기존 한샘 공식몰은 가격·할인율·배지·리뷰 같은 정보는 충분했지만, 그 정보가 놓인 구조가 문제였습니다. 메인은 프로모션과 탐색 버튼이 한 슬라이드 안에 섞여 있었고, 세분화된 카테고리에서는 원하는 상품까지 가는 경로가 잘 보이지 않았습니다. 정보 요소는 그대로 두고 화면마다 역할을 나눠 위계를 다시 세우는 것, 그리고 그 위에 과하지 않은 인터랙션을 얹는 것을 목표로 했습니다.

Main Page Redesign

기존 메인은 전체 화면을 채우는 슬라이드 안에 가구·홈리빙·인테리어 버튼이 배경 이미지와 구분 없이 배치되어 있어, 클릭 가능한 요소임을 인지하기 어려운 구조였습니다. 프로모션 배너와 탐색 동선이 한 화면에 혼재된 점도 사용자의 시선을 분산시킨다고 판단했습니다.
리디자인에서는 역할을 분리했습니다. Hero는 프로모션 배너로만 구성하고, 이어지는 Space Curation 섹션(거실·침실)에서 공간 사진 위 핀으로 상품을 보여준 뒤, Best Seller 8개로 구매 탐색을 이어가는 흐름을 잡았습니다. 마지막 섹션에는 리모델링 시공 사례와 CTA를 배치해 '공간 전체를 바꾸는 브랜드'라는 메시지로 마무리했습니다.

리디자인에서는 탐색 흐름을 단계별로 정리했습니다. 상단의 중분류 탭과 소분류 칩을 하나의 sticky 영역으로 묶어 스크롤 중에도 카테고리를 바꿀 수 있게 하고, 탭을 바꾸면 스크롤을 탭 바로 아래로 되돌립니다. 카테고리 메인에는 Hero(소개와 CTA), 에디터 추천 컬렉션, 이벤트 배너, 인기 상품 순으로 배치해 '탐색 → 발견 → 구매 고려'의 흐름을 만들었습니다. 중분류 탭에 들어가면 월간 인기 상품과 필터 바, 상품 그리드가 바로 이어져 조건을 좁혀 원하는 상품을 찾을 수 있습니다.

01

절제된 인터랙션 - "AI스러운" 기본값을 의도적으로 배제

  • AI 도구가 생성하는 UI에는 공통된 패턴이 있습니다. hover시 카드가 이동하고, 그림자가 과하게 설정되고, 이미지가 과하게 확대됩니다. 보는 관점에 따라 이런 효과가 나쁜 것만은 아니지만, 이 프로젝트에서는 CLAUDE.md에 명시하여 그런 패턴들을 의도적으로 배제하고, 절제된 인터랙션을 사용했습니다. 지금 코드에는 hover에 scale·translateY를 쓰는 곳이 한 곳도 없습니다.
  • 상품 카드 hover - 이미지 교체
    hover 시 두 번째 갤러리 이미지로 0.5초 동안 opacity가 바뀌며 전환됩니다. scale 확대나 translateY 이동을 함께 쓰지 않은 이유는, 이미지 교체와 겹치면 인터랙션이 과하다고 판단했기 때문입니다.
  • 토글 아이콘 - SVG path 교체
    공간 큐레이션의 상품 핀이 열릴 때 +가 -로 바뀝니다. 아이콘을 CSS rotate로 돌리지 않고, 열린 상태와 닫힌 상태의 SVG path 자체를 바꿔 그립니다. 위·아래·왼쪽·오른쪽 화살표도 아이콘 하나를 회전시키지 않고 방향마다 따로 그렸습니다. CSS와 컴포넌트 전체에 rotate()는 한 번도 쓰지 않았습니다.
  • 상세페이지의 영상 - 화면에 보일 때만 재생
    IntersectionObserver로 영상이 화면에 절반 이상 보이면 재생하고, 벗어나면 일시정지하고, 다시 들어오면 멈춘 지점부터 이어서 재생합니다. 영상 파일 주소는 처음 화면에 들어올 때 넣기 때문에, 그 전까지는 영상을 내려받지 않습니다. 영상 자리가 크기 정보 없이 300×150 비율로 잡혀 재생되면서 아래 내용이 밀리던 문제도 있어, 서버에서 mp4 헤더를 읽어 원본 비율로 자리를 미리 잡게 했습니다. 사용자가 보지 않는데 반복 재생되는 영상은 노이즈라고 판단했습니다.
02

재사용 가능한 인터랙션 패턴

  • 가로 스크롤 버튼 패턴
    창 크기가 바뀔 때 스크롤 버튼이 뒤늦게 나타나거나 사라지는 현상을 막기 위해 ResizeObserver가 스크롤 영역 너비를 지속적으로 감시합니다. 측정 완료 전 버튼이 잘못 노출되는 깜빡임을 막기 위해 canScroll 초기값을 null로 두었고, null인 동안은 버튼을 숨깁니다. visibility: hidden 대신 display: none을 쓴 이유는, visibility: hidden이 공간을 그대로 차지해 레이아웃이 어긋나기 때문입니다. ProductGallery.tsx(상품 썸네일), ReviewSection.tsx(포토 리뷰), ProductVariantPicker.tsx(구성 선택 카드) 세 곳에 같은 패턴을 썼습니다.
  • 모달 패턴
    상위 요소에 transform이 적용된 경우 position: fixed 자식의 기준점이 부모로 바뀌어 위치가 틀어지는 문제를 막기 위해 createPortal로 모달을 document.body에 직접 마운트합니다. 장바구니 담기 모달, 포토 리뷰 모달, 전체 필터 패널, 헤더 드로어 네 곳이 같은 방식입니다. overflow: hidden 적용 전 스크롤바 너비를 측정해 paddingRight로 보정하고, 닫힐 때 원래 값으로 복원합니다. 처음에는 두 곳만 원래 값을 저장했다가 되돌리고 나머지는 빈 값으로 지우고 있어서, 네 곳 모두 같은 방식으로 맞췄습니다. Esc 키 닫기는 keydown 이벤트로 처리하고 cleanup에서 removeEventListener합니다.
  • 드롭다운 공통 패턴
    드롭다운 바깥을 클릭하거나 Escape 키를 눌렀을 때 닫히도록 mousedown과 keydown 이벤트를 등록하고, useEffect cleanup에서 두 리스너를 모두 제거합니다. 컴포넌트가 사라진 뒤에도 이벤트가 남아있는 문제를 방지하기 위한 처리입니다. 필터 바, 정렬, 상세 옵션, 주문서 배송 메모 드롭다운에 같은 패턴을 썼습니다.
03

마크업 & CSS 설계

  • 페이지당 h1 하나
    홈은 Hero 첫 슬라이드 타이틀, 카테고리는 CategoryHero 타이틀, 상세는 상품명을 h1로 두고 로고에는 h1을 쓰지 않았습니다. 장바구니·주문서·검색·매거진·이벤트 페이지도 h1은 하나씩입니다. 섹션과 배너 제목은 h2부터 시작합니다. 타이포 토큰의 h1~h6은 크기 단계 이름일 뿐이라, 태그는 문서 구조를 기준으로 고르고 크기는 화면 위계에 맞는 토큰을 따로 골랐습니다.
  • 컴포넌트와 스타일을 한 쌍으로 - CSS Modules
    컴포넌트마다 같은 이름의 .module.css를 짝으로 두었습니다. 클래스 이름이 컴포넌트 단위로 격리되어 섹션이 늘어나도 이름 충돌을 신경 쓸 필요가 없고, 컴포넌트를 지우면 스타일도 함께 정리됩니다. 미디어쿼리는 각 파일 맨 아래 반응형 블록에 모아 크기가 바뀌는 지점을 한 곳에서 확인할 수 있게 했습니다.
  • 색·글자·radius는 토큰으로
    컬러 15개, 폰트 크기 16단계(가격·평점 전용 포함), 굵기 5단계, radius 3단계를 globals.css의 :root에 정의했습니다. 컴포넌트에서는 색, 글자 크기, 굵기, radius 값을 직접 쓰지 않습니다. 로고(22px, 800)나 이미지마다 다른 오버레이 그러데이션처럼 한 곳에서만 쓰는 값은 예외로 두고, 이유를 CLAUDE.md에 적었습니다.
  • 텍스트는 정렬선 하나에
    배경과 이미지는 화면 끝까지 채우되, 글자가 시작하는 위치는 1440px 컨테이너의 정렬선 하나에 맞췄습니다. 풀블리드 섹션은 이 위치를 계산한 --align-inset 변수를 패딩으로 써서(24곳), 섹션마다 40px·60px 같은 값을 따로 넣지 않습니다. 본문 폭을 좁힌 상세페이지 하단 영역은 40px이 8곳에 직접 적혀 있었는데, --detail-pad 토큰(min(40px, 컨테이너 여백))으로 바꿔 화면 폭별 미디어쿼리도 함께 지웠습니다. 모바일 프로모션 배너가 정렬선보다 24px 안쪽에 있던 것도 이때 맞췄습니다.
04

반응형 & 접근성

  • 브레이크포인트는 1024 / 768 / 480px 세 지점
    데스크톱 기준(max-width)으로 세 지점만 두었습니다. 각 지점에서 :root의 --container-pad(60 → 40 → 24 → 16px)와 제목 크기 토큰만 다시 정의하면, 정렬선과 제목 크기가 모든 섹션에서 함께 줄어듭니다. 콘텐츠가 실제로 부딪히는 곳에만 컴포넌트 전용 지점을 예외로 두었습니다. 헤더는 메뉴가 겹치기 시작하는 1440px·580px을 실측해서, Hero는 큰 제목 글자의 좌우 여백을 1280px부터 4 → 2 → 0px로 보정하려고 지점을 두었습니다. Footer(1280px)와 공간 큐레이션(580px)까지 예외 지점 모두 실측한 이유를 CSS 주석으로 남겼습니다.
  • 상품 그리드는 열 수를 직접 지정
    가격·할인율·배지가 함께 들어가는 카드라 열이 많아지면 텍스트가 깨집니다. auto-fill에 맡기지 않고 4열 → 3열(≤1024) → 2열(≤768)로 명시했습니다. 모바일(≤768)에서는 흩어져 있던 필터 진입점을 전체 필터 드로어 하나로 모았습니다.
  • 키보드와 스크린리더
    점검해 보니 드롭다운 옵션 마크업이 세 가지로 갈려 있었고, 카테고리 필터는 키보드로 옵션을 고를 수 없었습니다. 상세 정렬·옵션은 role="option" 안에 button이 들어간 잘못된 구조였습니다. 화살표 키 이동까지 갖춘 listbox를 새로 구현하는 대신, 구현하지 않는 동작을 role로 약속하지 않도록 드롭다운을 '열고 닫는 버튼 + 버튼 목록'으로 통일했습니다. 트리거는 aria-expanded로 열림 상태를 알리고, 옵션은 Tab으로 이동해 Enter로 고르며, 모두 Esc로 닫힙니다. 아래 그리드를 거르는 소분류 칩은 aria-pressed로 선택 상태를 알리고, 헤더 검색은 combobox로 고쳤습니다. hover로만 열리는 헤더 메가메뉴와 Footer 패밀리사이트는 예외로 남기고 CLAUDE.md에 적었습니다.
01

실제 커머스 제약을 반영한 상품 데이터 설계

  • 한 상품이 여러 카테고리에 동시에 소속됨
    호텔침대는 퀸침대이면서 동시에 수납침대일 수 있습니다. 이런 실무적 상황을 표현하기 위해 주 분류 경로(category[ ])와 추가 소속(categoryTags[ ])을 분리해서 저장하되, getByCategory( ) 함수가 두 필드를 동시에 검색하도록 설계했습니다. 어느 쪽 분류로 진입해도 상품이 노출됩니다.
  • 컬러 차이와 구성 차이는 서로 다른 단위로
    색상만 다른 변형(화이트/차콜 등 컬러옵션)은 하나의 SKU로 묶어 colors[ ] 배열로 처리하고, 구성이 다른 변형(단품 vs 매트 세트)은 별도 SKU로 분리했습니다. 카드를 몇 장 보여줄지가 UI 결정이 아니라 데이터 구조 설계에서 결정된다는 것을 직접 구현하면서 실감했습니다.
  • 필터 연동을 위한 구조적 중복 저장
    카테고리 페이지 필터는 그 카테고리의 상품 요약 목록을 훑어서 실제 옵션이 있는 축(사이즈, 색상 등)만 보여줍니다. 필터는 상세 데이터를 읽지 않기 때문에, filterAttributes를 카드 요약(summaries[ ])과 상세 페이지 데이터(variantDetails) 양쪽에 모두 적어야 했습니다. 나중에 한쪽만 고치는 실수를 막으려고, 이 중복이 일부러 둔 것이라는 점을 CLAUDE.md에 적어 두었습니다.
  • 리뷰 사진 경로를 빌드 전에 검사
    리뷰 사진 경로를 손으로 적다 보니 복사·붙여넣기 실수로 빈 사진이 나오거나, 다른 상품 폴더를 가리켜 엉뚱한 사진이 보이는 경우가 있었습니다. 빌드 직전에 모든 리뷰 사진 경로가 실제 파일과 맞는지 확인하는 스크립트를 만들었고, 처음 돌렸을 때 오류 61건이 나왔습니다. 파일이 아직 없는 44개는 TODO 주석으로 표시해 두었습니다.
02

가벼운 상태 관리 - 목적에 맞는 도구 선택

  • 장바구니 - Zustand + persist
    페이지를 이동해도, 새로고침해도 장바구니가 유지되어야 하므로 persist 미들웨어로 localStorage에 저장했습니다. 같은 상품이라도 옵션이 다른 경우를 구분하기 위해 itemKey(productId, optionLabel) 함수로 복합 키를 만들어 항목을 관리합니다. 헤더의 장바구니 개수는 셀렉터로 총 수량만 구독해서, 총 수량이 바뀔 때만 헤더가 다시 그려집니다. 추가 금액이 있는 옵션을 담을 때는 그 금액을 판매가와 정가 양쪽에 더합니다. 판매가에만 더하면 할인율이 실제보다 크게 계산되기 때문입니다. 할인율도 같은 이유로 반올림하지 않고 내림합니다(19.6%는 20%가 아니라 19%).
  • UI 상태 - 컴포넌트 로컬 useState
    검색창 열림 여부, 헤더 스타일, 리뷰 정렬 순서, 포토 리뷰 모달, 공간 핀 활성 ID, 위시리스트 토글은 모두 컴포넌트 로컬 useState로 처리했습니다. 페이지를 벗어나면 초기화되어야 하는 상태이고, 다른 컴포넌트와 공유될 이유가 없기 때문입니다.
03

서버/클라이언트 경계와 데이터 페칭 설계

  • App Router의 기본값은 서버 컴포넌트
    "use client"를 남발하면 서버 컴포넌트의 이점(HTML 직접 렌더링, 클라이언트 번들 절감)이 사라집니다. 이 프로젝트에서는 브라우저 기능(useState, useEffect, 이벤트 핸들러)이 필요한 컴포넌트에만 "use client"를 선언했습니다.
  • 파일 기반 레지스트리를 서버에서 직접 호출
    상품 상세 페이지(app/products/[id]/page.tsx)와 카테고리 페이지(app/category/[slug]/page.tsx)는 서버 컴포넌트입니다. getProductDetail( ), getByCategory( ) 함수를 페이지 파일 안에서 직접 호출해 데이터를 가져오며, 이 함수들은 외부 API가 아닌 app/lib/products/index.ts의 파일 기반 레지스트리를 조회합니다. 이 두 페이지의 데이터 조회 코드는 서버에서만 실행됩니다.
  • 정적 데이터에서 API 소비 구조로 부분 전환
    인터랙션과 화면 구조를 먼저 정적 데이터로 검증한 뒤, 실제 비동기 데이터가 필요한 영역(검색 자동완성, 검색 결과 페이지, 장바구니 모달 추천)만 Route Handler(app/api/products/*)로 연결했습니다. 서버 컴포넌트가 자신의 API를 다시 호출하는 불필요한 HTTP 왕복을 피하기 위해, 서버 페이지는 데이터 레지스트리를 직접 호출하는 기존 방식을 유지하고 클라이언트 컴포넌트만 fetch로 전환하는 하이브리드 구조로 만들었습니다. 필터·검색 로직은 이동하지 않고 기존 모듈에 그대로 둔 채 API가 감싸기만 해서, 두 경로의 결과가 어긋날 수 없습니다. 상품 상세 조회 API는 존재하지 않는 id로 요청해도 에러 메시지에 그 id를 넣지 않습니다. 사용자 입력을 검증 없이 응답에 그대로 돌려주지 않기 위해서입니다.
  • 결정 사례 - 상품 상세 페이지
    처음에는 상단 영역(ProductOverview)과 하단 탭 영역(ProductTabLayout)을 통째로 클라이언트 컴포넌트로 두어, 그 안의 상품명·정보 패널·섹션 콘텐츠까지 클라이언트 번들에 들어가 있었습니다. 상단은 갤러리 이미지 순서 state 하나 때문에 클라이언트였던 것이라, 그 state를 ProductGallery 안으로 옮겨 상단 영역 전체를 서버 컴포넌트로 바꿨습니다. 탭 영역은 탭 전환만 클라이언트에 두고, 탭 안의 패널 4개는 서버에서 그려 props로 넘깁니다. 그 결과 정보 패널, 배송 안내, 상세 섹션, 구매 전 안내 등 6개 컴포넌트가 클라이언트 번들에서 빠졌습니다. 전송 JS는 306.7KB에서 300.2KB로 조금 줄었고, 모바일 TBT(메인 스레드가 막힌 시간)가 70~230ms에서 10~50ms로 줄었습니다. 옵션 가격 변경, 장바구니 담기, 탭 이동, 리뷰 정렬, 포토 모달 등 상세 인터랙션 42개 항목을 전후로 확인했습니다.

Design Decisions

주요 디자인 결정과 그 이유

포인트 컬러는 빨강 하나만

침대·소파·주방·소품까지 상품군이 넓어 사진마다 색이 제각각입니다. 포인트 컬러를 따로 두면 상품 사진과 부딪혀서, 바탕은 화이트·그레이로 두고 빨강은 할인율·할인 금액·상품 배지와 입력 오류처럼 알려야 하는 곳에만 썼습니다. 판매가는 빨강 대신 굵기로만 강조했습니다. 별점도 노랑 대신 검정으로 칠했습니다. 쓰던 노랑(#F5A623)은 흰 배경에서 2.03:1로, 아이콘 같은 비텍스트 요소 기준인 3:1에도 못 미쳤습니다.

빨강은 명도만 낮춰서

처음 쓴 #FF4D4F는 흰 배경 대비가 3.27:1로, 작은 글씨 기준인 4.5:1(WCAG AA)에 못 미쳤습니다. 색상은 그대로 두고 명도만 낮춘 #D92D2F로 바꿔 흰 배경에서 4.81:1, 회색 배경에서 4.53:1이 나오도록 했습니다. 배지 색은 원래 상품 데이터에 hex로 따로 적혀 있었고(#FE5A5D 23개, 이 색도 3.07:1), 그래서 상품마다 빨강이 조금씩 달랐습니다. 데이터에서 색을 지우고 배지는 CSS에서 이 토큰으로만 칠하게 바꿨습니다. 배지 종류별 색 필드를 두는 방식도 검토했지만, 배지가 모두 빨강으로 통일되면서 필드 자체를 없앴습니다.

선 색은 두 가지로

토큰 없이 직접 적은 연회색 선이 5가지(#EFEFEF, #E2E2E2, #EEE, #DDD, #E5E5E5) 섞여 있었습니다. 가장 많이 쓰던 #EFEFEF(12곳)는 회색 배경 위에서 1.08:1로 거의 보이지 않아 뺐습니다. 사이트 대부분의 테두리와 섹션 구분선은 원래 쓰던 #D0D0D0으로 맞추고, 상세 하단 정보 영역과 Footer처럼 촘촘한 정보를 나누는 얇은 선만 #E5E5E5로 정리했습니다.

구성이 다르면 카드도 따로

색상만 다른 상품은 카드 한 장에 컬러 칩으로 보여주고, 사이즈나 매트리스 포함 여부처럼 사진과 가격이 달라지는 구성은 카드를 따로 나눴습니다. 같은 시리즈를 '최저가부터' 카드 한 장으로 묶는 방식도 검토했지만, 카드 사진과 실제 구성이 달라질 수 있어 쓰지 않았습니다. 색상에 추가 금액이 붙는 경우는 색상 옵션에 금액을 함께 두고, 가격만 다른 옵션은 카드를 나누지 않고 가격 옵션으로 처리했습니다.

Code

getByCategory

주 분류와 추가 소속을 함께 검색해, 어느 분류로 들어와도 상품이 보이게 합니다.

export function getByCategory(
  cat: string,
  limit?: number
): ProductSummary[] {
  const result = catalog
    .filter((p) =>
      p.category.includes(cat) ||
      p.categoryTags?.includes(cat))
    .sort((a, b) => b.salesCount - a.salesCount);
  return limit ? result.slice(0, limit) : result;
}

itemKey

같은 상품도 옵션이 다르면 장바구니에서 다른 항목으로 구분합니다.

function itemKey(
  productId: string,
  optionLabel?: string
) {
  return optionLabel
    ? `${productId}__${optionLabel}`
    : productId;
}

Retrospective

  • 규칙을 먼저 쓰고 시작한 것
    컬러·타이포 토큰, hover 규칙, 상품 데이터 구조를 CLAUDE.md에 먼저 정리하고 Claude Code와 작업했습니다. 화면이 늘어날수록 판단 기준이 흔들리기 쉬운데, 기준이 문서로 남아 있으니 어긋난 부분을 바로 찾아 되돌릴 수 있었습니다.
  • 늦게 발견한 폰트 문제
    데스크톱 Lighthouse 점수만 보고 넘어갔다가, 모바일에서 Performance 55가 나온 뒤에야 원인을 찾았습니다. Pretendard 다섯 가지 굵기를 서브셋 없이 받아 폰트만 약 3.8MB였고, 토큰으로 정의해 둔 300 굵기는 파일이 없어 400으로 그려지고 있었습니다. Variable 폰트와 다이나믹 서브셋으로 바꾸자 전체 92조각 중 홈에서는 필요한 13조각만 받게 되어 폰트 전송량이 336KB로 줄었고, 모바일 Performance는 55에서 76이 되었습니다(당시 측정 환경 기준). 토큰을 정의하는 것과 실제로 그렇게 렌더링되는지 확인하는 것은 별개라는 걸 배웠습니다.
  • 지운 줄 알았던 Tailwind
    CSS Modules로 통일하면서 Tailwind 불러오기만 지우고, layout.tsx의 클래스 3줄과 패키지·설정 파일은 그대로 남겨 두었습니다. 화면에는 아무 효과가 없는 코드라 오래 눈에 띄지 않았습니다. 클래스를 CSS로 옮기고 패키지를 지운 뒤, 모든 페이지의 전후 스크린샷을 픽셀 단위로 비교해 레이아웃이 그대로인 것을 확인했습니다. 쓰지 않는 컴포넌트 파일 7개도 이때 함께 지웠습니다.
  • 남아 있는 gif
    상세 설명에 gif가 21개(약 32MB) 남아 있었습니다. 화면에 보일 때만 불러오는 영상 방식이 이미 있어서, 3MB가 넘는 4개부터 mp4로 바꿨습니다. 4.4MB였던 파일이 1.0MB, 3.4MB였던 파일이 331KB가 되는 등 4개 합계가 14.9MB에서 2.4MB로 줄었습니다. 남은 17개(약 17.3MB)도 같은 방식으로 바꾸고, 어디서도 쓰지 않는 3개는 지울 예정입니다.
  • 포커스 스타일
    Esc 닫기와 aria 속성은 챙겼지만, 키보드로 이동할 때 보이는 포커스 표시는 브라우저 기본값에 맡겼습니다. 절제된 톤에 맞는 :focus-visible 스타일을 따로 설계할 생각입니다.
